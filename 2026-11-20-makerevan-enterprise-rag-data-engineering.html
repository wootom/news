엔터프라이즈 RAG 실서비스 실패의 원인은 모델이 아닌 데이터 엔지니어링 부재

RAG 실서비스 실패는 모델이 아닌 버전, 동기화, 권한 등 데이터 엔지니어링 문제

영상 발화자의 견해·경험을 원문에 근거해 정리한 요약입니다.

데모와 실서비스의 구조적 차이

  • PDF를 청크로 자르고 임베딩 벡터를 생성해 벡터 DB에 저장하는 5단계 과정은 30분 내 데모 구현이 가능합니다.
  • 데모 환경은 문서가 한 번만 입력되고 변경·삭제·권한 제한이 없는 정적 가정을 전제로 하지만, 실서비스에서는 이 가정이 모두 깨집니다.

문서 버전 관리와 최신성 보장

  • 문서 개정 시 이전 버전 청크가 벡터 DB에 잔존하면 폐기된 규정을 근거로 답변하는 오류가 발생하며, 이는 프롬프트 수정으로 해결할 수 없습니다.
  • 문서 고유 ID와 버전 번호, 유효 기간을 메타데이터로 저장하고 검색 시 최신 버전만 필터링하는 데이터 모델링 방식이 필요합니다.

증분 동기화와 삭제 처리 전략

  • 수십만 개 문서 규모에서 전체 재임베딩은 비효율적이므로 수정 시각 기준 증분 적재를 사용하지만, 삭제된 행은 수정 시각으로 감지되지 않는 함정이 있습니다.
  • 삭제된 문서가 검색에 잔존하는 문제를 해결하기 위해 소프트 삭제 표시나 CDC(Change Data Capture)를 활용해 추가·수정·삭제 이벤트를 동기화해야 합니다.

스키마 변경 대응과 데이터 계약

  • 원본 데이터 소스의 필드 구조 변경 시 파이프라인이 멈추지 않고 빈 컬럼으로 적재되면 검색 품질이 조용히 저하되는 장애가 발생합니다.
  • 적재 단계에서 필수 컬럼 비어있음이나 ID 중복을 검사하는 dbt 테스트를 적용하고, 원본 팀과 컬럼 형식을 미리 약속하는 데이터 계약을 통해 실패를 명시적으로 처리해야 합니다.

멱등성 기반 재실행 안전장치

  • 단순 INSERT 방식은 작업 중단 후 재실행 시 동일 청크가 중복 적재되어 검색 결과 상위를 채우고 다른 근거를 밀어내는 문제를 일으킵니다.
  • 문서 ID, 버전, 청크 순번을 결합한 해시 ID를 생성하고 Postgres의 ON CONFLICT 구문 등을 활용해 업서트(Upsert) 방식으로 덮어쓰기 처리해야 멱등성을 확보할 수 있습니다.

검색 단계의 권한 통제와 동기화

  • 모든 문서를 단일 컬렉션에 저장하면 신입사원도 민감한 인사·계약 문서에 접근할 수 있으며, 프롬프트 기반 제한은 이미 검색된 정보 노출을 막을 수 없습니다.
  • 청크 생성 시 원본 문서의 접근 권한을 메타데이터로 저장하고, 검색 시 질문자의 부서·직급으로 필터링하며 Postgres 행 수준 보안(RLS)으로 강제해야 합니다.

도구 도입 기준과 AI 시대의 데이터 역량

  • Kafka, Spark, Kubernetes 등 복잡한 아키텍처는 실제 대용량·실시간 처리 문제가 있을 때만 도입해야 하며, 소규모 사내 RAG는 Postgres와 pgvector, Python 증분 적재로 충분합니다.
  • AI가 코드를 생성하더라도 데이터 정의, 신뢰성, 권한 규칙 등 업무 맥락은 인간이 결정해야 하며, SQL, 테이블 설계, 증분 적재, 테스트, 재실행 관리 5가지 핵심 역량이 필수적입니다.
