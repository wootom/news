도메인 스토리텔링은 해피 패스 중심의 공동 이해로 소프트웨어 품질을 높이는 협업 모델링 기법이다.

해피 패스부터 시각화해 도메인 전문가와 개발자의 공동 이해를 만드는 법.

01핵심 개요

  • 도메인 스토리텔링은 사람들이 함께 일하는 방식을 모델링해 도메인 지식을 비즈니스 소프트웨어로 변환하는 협업 기법으로 소개됐다.
  • 개발 전문지식 자체보다 개발자가 구축 대상 도메인을 이해하는 일이 훌륭한 비즈니스 소프트웨어의 핵심이라는 점을 강조했다.
  • 워크숍에서는 도메인 전문가의 실제 경험을 아이콘·화살표·텍스트 다이어그램으로 기록해 오해와 구성상의 허점을 찾는다.
  • 기본 사례와 정상 경로인 해피 패스를 먼저 모델링하고, 예외는 가정·참고로 남기거나 후속 논의에서 세분화한다.
  • 유스케이스 다이어그램이 기능 목록을 위한 명세라면, 도메인 스토리텔링의 산출물은 공동 기반이라는 점을 비교했다.

02핵심 주장 / 논점 구조

  • 도메인 스토리텔링의 목적은 엄밀한 명세를 대체하는 것이 아니라 도메인 전문가와 개발자 사이의 공동 이해를 구축하는 데 있다.
  • 훌륭한 비즈니스 소프트웨어를 만들기 어려운 이유는 기술 문제인 경우보다 개발자가 업무 도메인을 충분히 이해하지 못하는 경우가 많다고 설명했다.
  • 도메인 전문가에게는 실제 업무의 스토리를 듣고, 시스템 구현과 세부 명세의 고민은 개발자가 맡아야 한다고 말했다.
  • 바이브 코딩에서도 도메인 스토리텔링 다이어그램을 만든 뒤 이를 클로드에 제공하는 방식이 효과적이었다고 소개했다.

03소프트웨어 유지보수와 도메인 이해의 필요성

  • 소프트웨어는 요구사항 비대화, 버그, 구조 이상 등으로 건강하게 성장하지 못할 수 있으며 망가진 코드는 자가 수복되지 않는다고 설명했다.
  • 문제 있는 소프트웨어를 개선하려는 노력 자체가 문제를 만들 수 있어 무분별한 코드 리뷰와 리팩터링은 코드를 병들게 할 수 있다고 말했다.
  • 도메인 관련 문제를 반복적으로 해결하려면 주제 전문가와 긴밀하게 협력하는 개발자가 필요하며, 이를 FD 업무와 유사하게 봤다.
  • 최고경영책임자, 운영책임자, 임원, 팀장, 도메인 전문가도 업무 처리 이해와 전산 담당자와의 소통 개선을 위해 읽을 만한 책으로 소개됐다.

04도메인 스토리와 워크숍 모델링 방식

  • 도메인 스토리텔링은 사람들의 협업 방식을 강조하는 협업 모델링 기술이며, 사람을 기준으로 업무 상호작용을 설명한다고 정리했다.
  • 도메인 전문가는 실제 현장 경험이 담긴 구체적 사례를 이야기하는 스토리텔러이고, 추상적 가정이나 추측성 이야기는 피해야 한다고 설명했다.
  • 워크숍 진행자는 전문가의 이야기를 간단한 아이콘, 화살표, 텍스트로 구성된 다이어그램으로 기록한다.
  • 대화의 시각화는 오해·모순·구성상의 허점을 드러내며, 참가자의 피드백과 참여를 쉽게 만드는 장점이 있다고 말했다.

05해피 패스 우선과 예외 처리의 분리

  • 첫 도메인 스토리에서는 가장 일반적인 결과인 정상 경로, 즉 해피 패스를 먼저 다루고 나머지 사례는 나중에 질문한다고 설명했다.
  • 엣지 케이스와 조건 분기를 모두 다이어그램에 넣으면 구현에 가까운 명세가 되어 도메인 전문가와의 공동 이해를 방해할 수 있다고 말했다.
  • 모델링 캔버스의 가정은 스토리 실행에 필요한 전제 조건을, 참고는 이미 배송이 시작된 주문 취소 같은 중요한 엣지 케이스를 기록하는 용도라고 설명했다.
  • 도메인 스토리 다이어그램은 공동 이해용으로 순결하게 유지하고, 상세 플로우차트는 구현 담당자끼리 별도로 다루어야 한다고 정리했다.

06시나리오 기반 모델링의 세분화 전략

  • 3장의 시나리오 기반 모델링에서는 시나리오와 도메인 스토리를 같은 의미로 설명하며, 여러 사례를 다루는 방법을 제시했다.
  • 영화관 사례에서 1회 관람권 판매처럼 빈도가 높은 흐름을 우선 모델링하고, 연간권처럼 다른 사례는 별도 논의 대상으로 둘 수 있다고 했다.
  • 기본 사례 또는 80% 사례와 정상 경로를 먼저 모델링한 뒤, 필요한 영역만 선택적으로 더 깊게 파고드는 방식을 권했다.
  • 일반적 사례나 해피 패스를 식별하기 어려운 도메인에서는 간단한 사례, 보통 사례, 어려운 사례, 아주 어려운 사례로 나눠 질문할 수 있다고 소개했다.
  • 한국의 비상사태 특별 전담팀 사례에서는 정상 경로를 묻기보다 가장 간단한 업무와 가장 어려운 업무를 묻자 더 풍부한 답변을 얻었다고 설명했다.

07공통 기반 구축과 유스케이스의 차이

  • 도메인 전문가의 암묵지를 추출하려면 전문가가 쓰는 용어와 의미, 업무 처리 과정, 주요 단계, 이해관계자를 파악하는 공통 기반이 필요하다고 설명했다.
  • 공통 기반이 형성되면 프로젝트 범위에 속하는 업무와 그렇지 않은 업무를 논의할 수 있어, 개발 중 ‘이것도 돼야 한다’는 범위 확대를 줄일 수 있다고 말했다.
  • 반복 활동, 다른 위치에서 일어나는 스토리 부분, 조직 경계, 부분 도메인은 그룹으로 묶어 복잡한 다이어그램을 한눈에 이해하기 쉽게 만든다고 설명했다.
  • 유스케이스 다이어그램은 시스템 구현을 위한 명세로서 기능 목록을 도출하고 엣지 케이스를 담지만, 도메인 스토리텔링은 사람들의 상호작용과 순서를 다룬다고 비교했다.
  • 유스케이스의 산출물이 기능 목록이라면 도메인 스토리텔링의 궁극적 산출물은 용어·프로세스·이해관계자를 공유하는 공동 기반이라고 정리했다.
