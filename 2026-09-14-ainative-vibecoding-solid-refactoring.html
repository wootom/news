바이브코딩 코드베이스를 SOLID와 계층 구조로 점검하는 리팩토링 방송이다.

SOLID와 계층형 아키텍처로 바이브코딩 코드베이스를 점검하는 방법을 다룬다.

01핵심 개요

  • 방송은 바이브코딩으로 만든 코드베이스를 대상으로 SOLID 원칙과 계층 분리 관점의 점검 과정을 다룬다.
  • 좋은 코드의 기준으로 파일 하나가 하나의 책임을 갖는 SRP, 즉 단일 책임 원칙을 우선 제시한다.
  • React 프로젝트에서는 Components를 Presentation, Hooks를 Business Logic으로 보고 역할 분리를 설명한다.
  • Infrastructure에는 DB·API·Google 같은 외부 서비스가 포함되며 Presentation이 직접 의존하지 않아야 한다고 말한다.
  • 코딩 에이전트에는 한 번에 긴 지시를 주기보다 멀티턴으로 맥락과 작업 과정을 구성하는 방식을 언급한다.

02핵심 주장 / 논점 구조

  • 코드베이스 리팩토링의 출발점으로 좋은 코드의 기준과 중요한 파일·폴더를 파악하는 일을 제시한다.
  • SOLID 원칙 준수 여부를 코드베이스 점검 항목으로 삼고, 리팩토링 전에 구조를 검사하자고 말한다.
  • 바이브코딩에서도 코드를 계속 유지·개선하려면 개발자가 구조와 도메인을 이해해야 한다고 설명한다.

03SOLID 원칙과 단일 책임 기준

  • SRP는 Single Responsibility Principle로, 하나의 파일이 하나의 책임을 가져야 한다는 원칙으로 설명된다.
  • OCP는 개방·폐쇄 원칙으로 소개되며, 새 기능을 추가할 때 기존 코드를 고치지 않고 작성할 수 있어야 한다고 말한다.
  • 한 파일에 여러 책임이 쌓이는 문제와 파일 분리 사이에는 트레이드오프가 있을 수 있다고 언급한다.

04Presentation·Business Logic·Infrastructure 분리

  • 코드를 Presentation, Business Logic, Infrastructure의 세 그룹 또는 계층으로 나누는 방식을 제시한다.
  • Presentation은 사용자 입력과 UI를 맡고, Business Logic은 UI와 외부 서비스 사이의 로직을 담당한다고 설명한다.
  • Infrastructure에는 DB, API, Google 등 외부 시스템이 포함되며, Presentation이 이를 직접 다루면 안 된다고 말한다.
  • 계층 구조의 핵심은 Presentation과 Infrastructure 사이에 Business Logic을 두는 것이라고 강조한다.

05React와 Next.js 프로젝트의 계층 적용

  • React 프로젝트에서는 Components를 Presentation Layer, React Hooks를 Business Logic으로 대응시킨다.
  • Components 안에 Presentation·Business Logic·Infrastructure의 책임이 모두 들어가면 좋지 않은 코드의 특징이라고 말한다.
  • Next.js 서버 구조에서는 Presentation, Service, Repository·Provider로 역할을 나누는 예시를 든다.
  • 단순한 계산처럼 작은 경우에는 한곳에 두는 방식도 가능하지만, 일반적인 구조로는 권하지 않는다고 설명한다.

06관심사 공통화와 AOP 적용 수단

  • 로깅과 트랜잭션처럼 핵심 기능과 분리되는 공통 관심사를 AOP의 맥락에서 설명한다.
  • 적절한 공통화가 중요하며, 기능과 무관한 로직을 중복해 넣지 않는 방향을 언급한다.
  • JavaScript 프로젝트에서는 HOC를 활용해 withLogging처럼 새 함수를 감싸는 방식을 예로 든다.
  • Middleware, Global Exception Filter, Guard도 공통 관심사를 처리하는 수단으로 함께 거론한다.

07코딩 에이전트와 도메인 이해의 과제

  • LLM은 컨텍스트 안의 토큰과 attention에 기반하므로, 작업을 멀티턴으로 구성하는 일이 중요하다고 말한다.
  • 에이전트에게 중요한 폴더와 파일을 읽게 하고, 문제를 발견한 뒤 해결 절차를 진행하는 흐름을 언급한다.
  • 코딩 에이전트와 협업하려면 개발자가 프로젝트 전반과 도메인 용어를 이해해야 한다고 설명한다.
  • Domain Storytelling을 개발자와 도메인 전문가가 용어집을 만들고 소통하는 데 유용한 책으로 소개한다.
  • 인프라 선택과 데이터베이스 운영 언급: Supabase는 설정이 쉽지만 Pro 요금제에 대한 우려를 언급하고, AWS RDS와 비교해 말한다.
  • 인프라 선택과 데이터베이스 운영 언급: Neon을 연결해 보려 하며 Google Login, Social Login 같은 외부 연동은 Infrastructure로 분류한다.
  • 인프라 선택과 데이터베이스 운영 언급: Postgres를 선호한다고 말하고, Supabase의 RLS가 중요하다고 언급한다.
  • 인프라 선택과 데이터베이스 운영 언급: 데이터베이스 마이그레이션에서는 이전 데이터, 보안 그룹, 연결, Unicode 인코딩과 이모지 저장 문제를 고려해야 한다고 말한다.
