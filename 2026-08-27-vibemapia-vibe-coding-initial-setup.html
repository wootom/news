방송 성격실시간 라이브 코딩 스트림, 기획부터 인프라 세팅 착수까지 약 2.5시간 진행

02핵심 기능/내용 구조

1
문제 정의와 요구사항 정리 (AI 없이 직접)화자는 PT 6개월 차인데 몸의 변화가 체감되지 않는다는 개인적 문제에서 출발해, 목표 중량 설정, 하루 루틴 기록, 영양 분석, 눈바디·인바디 기록 등 필요한 기능을 스스로 나열했다. 분량이 적고 개인 취향이 강한 이 단계는 AI에 위임하면 오히려 소통 비용만 커지므로 AI 없이 직접 정리하는 것을 원칙으로 제시한다 (07:19).
2
기술 스택 선정앱은 크로스플랫폼(Expo/X4, 리액트 네이티브 기반)과 타입스크립트를 선택해 앱과 서버를 동일 언어로 통일했고, 서버는 보일러플레이트가 크지만 프로덕션에 필요한 기능이 내장된 NestJS를, 배포는 Railway를, 데이터베이스는 처음엔 Cloudflare를 고려했다가 논의 끝에 Supabase로 전환했다.
3
페이블(Fable) 모델로 초기 기획 검증코딩이 아닌 "생각을 깊게 하는" 용도로 느리고 비싼 페이블 모델을 선택해, 비개발자 관점의 요구사항을 붙여넣고 모호하거나 누락된 부분을 지적받는 방식으로 기획서를 보완했다 (24:24).
4
데이터 모델 확정 전 유저 스토리 도출AI가 곧바로 데이터 모델을 설계하려 하자, 먼저 각 기능의 유저 플로우/유저 스토리를 P0·P1·P2 우선순위로 뽑게 한 뒤 데이터 모델로 넘어가는 순서를 강제했다 (49:36).
5
기능 개발 순서는 중요도가 아닌 DB 의존관계 기준데이터베이스는 되돌리기 번거로우므로, 의존 관계가 적은 데이터를 참조하는 기능부터 개발하도록 지시해 스키마 변경 범위를 최소화하는 전략을 명시적으로 요구했다 (49:36).
6
"목표가 정말 달성되는 게 맞냐"는 재검증 질문데이터 모델이 확정된 뒤에도 그대로 넘어가지 않고, 확정안이 최초 목표를 정말 충족하는지 다시 물어보는 절차를 치트키로 소개하며 실제로 누락된 문제들을 찾아냈다 (62:06).
7
구현 100% 위임을 위한 사전 합의 프롬프트구현 단계에서는 손을 떼고 서브에이전트(오퍼스)가 단계별 구현-검증을 반복하도록, 메인 세션(페이블)은 방향성 관리자 역할만 하고 컨텍스트를 과도하게 소모하지 않도록 하는 별도 프롬프트를 입력했다 (69:44).
8
인프라 세팅을 브라우저 유즈로 에이전트에 위임Railway 프로젝트 생성·연결, Supabase 로그인·설정, API 키 발급 등을 에이전트가 브라우저를 직접 조작해 처리하도록 시켰고, 화자는 슈퍼베이스 클릭 조작법을 배우지 않고도 인프라 구축을 완료했다.

03기술적 맥락

화자는 타입스크립트를 "바이브 코딩의 깡패"로 표현하며, 앱·서버·웹·AI 서비스까지 하나의 언어로 대응 가능한 범용성 때문에 특별한 이유가 없다면 기본 선택지로 삼으라고 권한다. 크로스플랫폼 앱 프레임워크는 Expo(X4)와 Flutter 두 가지만 메이저로 보고, Flutter는 Dart 언어를 쓰기 때문에 서버와 언어를 통일할 수 없어 배제했다. 서버 프레임워크는 Express보다 보일러플레이트가 큰 NestJS를 택했는데, 이는 의존성 주입 등 초기엔 무거워 보이지만 프로덕션 단계에서 결국 필요해지는 구조를 프레임워크 레벨에서 강제해 개발자의 고민을 줄여주기 때문이라고 설명한다.

앱 서비스는 웹과 달리 풀스택 배포(클라이언트에서 DB 직접 연결)가 사실상 불가능하므로 반드시 별도 서버가 필요하다는 점, 그리고 Supabase처럼 클라이언트-DB 직접 연결을 지원하는 방식도 있지만 보안과 유지보수 관점에서 클라이언트-서버-DB로 분리하는 정석적 구조를 권장한다는 점을 강조한다. 데이터베이스와 스토리지 서비스 선택도 AI와 대화하며 결정했는데("Cloudflare가 낫지 않냐"는 질문에 에이전트가 응답), 이런 인프라 설정 작업을 사람이 직접 콘솔을 클릭하며 배우는 대신 에이전트의 브라우저 조작 기능에 맡기는 흐름을 실연했다.

04전략적 의미

이 방송의 핵심 메시지는 "바이브 코딩이 잘 되려면 AI에게 맡길 부분과 사람이 반드시 결정할 부분의 경계를 정확히 그어야 한다"는 것이다. 화자는 AI는 컴퓨터 안의 정보만 알고 있어 실제 타겟 유저(트레이너)의 기술 친화도나 문제 공감 수준 같은 현실 맥락을 모르기 때문에, 비즈니스 방향성 결정을 AI에 위임하는 것은 위험하다고 강조한다. 반대로 인프라 설정, 데이터 모델 초안 작성, 유저 스토리 초안 같은 반복적이고 검증 가능한 작업은 적극적으로 위임한다.

또한 "많이 만든다고 실력이 늘지 않는다"는 주장이 눈에 띈다. 화자는 자신도 15년간 요리를 해왔지만 요리사가 아니듯, 바이브 코딩도 반복만으로는 전문성이 생기지 않으며, PM 스킬(요구사항 명확화, 되묻기, 우선순위 결정)과 소프트웨어 공학 기본기(데이터베이스 의존관계, 아키텍처 분리 원칙)를 책과 이론으로 학습해야 실질적으로 성장한다고 역설한다. 이는 바이브 코딩 입문자들이 흔히 오해하는 "더 비싼 요금제, 더 많은 시행착오 = 실력 향상" 공식을 정면으로 반박하는 관점이다. 아울러 롱러닝 에이전트를 자랑하는 사례들에 대해 "토큰을 많이 쓰고 오래 도는 것 자체가 자랑거리가 아니라 비효율의 신호일 수 있다"는 회의적 시각도 제시한다.

06활용 시나리오

1
비개발자가 자신만을 위한 개인화 서비스를 기획할 때화자처럼 스스로가 타겟 유저인 경우, AI에 위임하지 말고 문제 정의와 핵심 요구사항만은 직접 정리한 뒤 AI에게 모호점을 되묻게 하는 절차를 그대로 적용할 수 있다.
2
앱+서버 조합의 MVP를 빠르게 검증하고 싶은 1인 개발자/창업가타입스크립트 통일, Expo+NestJS+Supabase+Railway 조합, 브라우저 유즈를 통한 인프라 자동 세팅 절차를 템플릿처럼 참고해 초기 스택 결정 시간을 단축할 수 있다.
3
바이브 코딩 실력을 늘리고 싶은데 무엇을 배워야 할지 모르는 학습자데이터베이스 의존관계 기반 개발 순서, PM 관점의 되묻기 스킬, 구현 위임 전 사전 합의 프롬프트 작성법 등을 실제 사례로 학습하고, 책(더 아트 오브 프로젝트 매니지먼트, 구글 소프트웨어 엔지니어는 이렇게 일한다, 도메인 주도 설계) 학습과 병행하는 방향을 참고할 수 있다.
4
에이전트에게 장시간 자율 구현을 맡기려는 개발자메인 세션은 방향성 관리자로 유지하고 실제 구현은 서브에이전트(오퍼스)에 위임하는 역할 분리, 그리고 에이전트가 오래 멈춰 있을 때 자랑거리로 착각하지 말고 원인을 점검하는 습관을 벤치마킹할 수 있다.

07현황 및 전망

방송이 끝난 시점까지 전체 9단계 구현 계획 중 0단계도 완료되지 않았으며, 화자는 실제 구현 진행 상황은 별도 녹화 영상으로 공개하고 다음 라이브(같은 주 금요일)에서 이어서 진행하겠다고 밝혔다. 서버 배포(Railway) 자체는 방송 중 성공했으나 실제 비즈니스 로직 구현은 이루어지지 않은 상태였다.

화자는 "예전에는 결과물을 만드는 것 자체에 학습 가치가 있었지만, 요즘은 AI가 어차피 잘 만들어주기 때문에 만드는 행위의 학습 가치가 크게 떨어졌다"고 진단하며, 앞으로는 코딩에 익숙해지는 것보다 탄탄한 이론·철학(소프트웨어 공학 원칙, PM 스킬)을 갖추는 쪽이 훨씬 중요해질 것이라는 전망을 제시한다. 또한 바이브 코딩으로 수익을 내는 난이도가 실제로는 매우 높으며, 검증되지 않은 고가 강의보다 스탠퍼드·YC 등에서 제공하는 무료 강의, 그리고 실질적 이론서를 우선하라는 조언을 덧붙였다. 본인의 전략으로는 컨설팅·강의로 먼저 고객 문제를 발견한 뒤, 반복되는 니즈를 소프트웨어(오픈소스 프로젝트 '아르고스' 등)로 전환해 B2B 커스터마이징·유지보수 계약으로 확장하는 방식을 소개했다.

08용어 사전

용어설명
바이브 코딩(Vibe Coding)AI(LLM 에이전트)에게 자연어로 요구사항을 전달해 코드 작성을 맡기고, 사람은 방향 제시와 검증 위주로 개발하는 방식
클로드 코드(Claude Code)Anthropic의 터미널 기반 AI 코딩 에이전트 도구. 이 방송에서 메인 개발 환경으로 사용됨
페이블(Fable)방송에서 언급된 AI 모델(느리고 비용이 높지만 깊은 사고에 강함). 코딩 실행보다 기획·검증 단계에서 사용됨
오퍼스(Opus)/소넷(Sonnet)Anthropic Claude 모델 라인업 중 코딩 구현 작업에 주로 쓰이는 모델들. 서브에이전트가 구현 작업에 사용
MCP (Model Context Protocol)AI 에이전트가 외부 도구·서버 기능(예: 운동 기록 저장)을 표준화된 방식으로 호출할 수 있게 하는 프로토콜
Expo(X4)리액트 네이티브 기반 크로스플랫폼(iOS/Android) 앱 개발 프레임워크, 타입스크립트 사용
리액트 네이티브자바스크립트/타입스크립트로 네이티브 모바일 앱을 만드는 프레임워크
NestJS(네스트JS)Node.js 기반 서버 프레임워크로 의존성 주입 등 구조화된 아키텍처를 프레임워크 레벨에서 제공
