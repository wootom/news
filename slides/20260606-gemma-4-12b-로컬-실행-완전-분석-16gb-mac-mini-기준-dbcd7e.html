02실행 환경 및 메모리 현실

  • 테스트 기기: Apple M4 Mac Mini 16GB RAM
  • 모델 다운로드 용량: 7.56 GB
  • 기본 컨텍스트(4,000 토큰) 로드 후 실제 점유: ~8 GB
  • 모델 로드 완료 시 Activity Monitor 메모리 사용량: 14.9 GB (대화 전)
  • OS·브라우저·앱 기본 점유: 약 2~3 GB → 실질 가용 RAM 감소 요인
  • 최대 컨텍스트(131,072 토큰) 실행 시 필요 RAM: 26 GB 이상 → 16GB 디바이스 불가

03주요 기술 업데이트 2가지

① 멀티모달 인코더 제거 (No Separate Encoders)

  • 기존 파이프라인: 이미지·오디오 입력 → 별도 인코더 → LLM (지연·번역 손실 발생)
  • Gemma 4 파이프라인: 인코더 레이어 제거 → 인코더 기능을 LLM 내부에 통합
  • 효과: 지연 감소 + 정확도 향상
  • 지원 입력 형식: 텍스트 / 이미지 / 오디오 (네이티브 멀티모달)

② 멀티토큰 예측 (MTP, Multi-Token Prediction)

  • LLM 인퍼런스 2단계 구조

- Pre-fill: 입력 메시지 소화 단계 → MTP 미적용 - Decoding: 응답 생성 단계 → MTP 적용 구간

  • MTP 메커니즘: 메인 12B 모델 + 소형 드래프트 모델 병행 실행

- 소형 모델이 다음 토큰을 선제 예측 → 메인 모델 검증·수용 - 수용률(Acceptance Rate): 약 60~70%

  • 속도 향상 수치(벤치마크 기준): 1.5~1.8배 빠른 응답 생성
  • 실측 토큰 생성 속도(Mac Mini M4 16GB): 약 11.69 tokens/sec

04LM Studio 활용 및 실습 내용

  • LM Studio: 로컬 모델 실행 + 로컬 API 서버 제공 앱
  • 로컬 서버 URL → 외부 애플리케이션에서 Gemma 4 호출 가능
  • 실습 내용: 인보이스 이미지 → Gemma 4 OCR 추출 → HTML 앱으로 파싱 결과 출력

OCR 테스트 결과

  • 추출 항목: Subtotal, Balance Due 등
  • 오류 사례: Balance Due → 1,296 출력 (실제 1,298) → 수치 부정확
  • 한계 원인: 범용 LLM은 OCR 특화 훈련 부재
  • 권장 대안 워크플로

- Gemma 4(범용) + OCR 특화 오픈소스 모델 + Python 추출 스크립트 병렬 실행 - 다수 결과 교차 검증 → 휴먼 인더루프 없이 정확도 확보

05활용 가능 유스케이스 및 한계 요약

  • 가능: 일반 대화, 코드 생성, 이미지 분석, 이메일 분류 자동화, 간단한 오피스 어드민
  • 한계: 정밀 OCR, 긴 컨텍스트(31K 토큰 초과), Claude Code 등 고토큰 하네스 직접 연결
  • 오픈소스 모델 일반 원칙: 파라미터 클수록 성능 우위 → 12B는 제약 있으나 16GB 디바이스 최적 선택지
