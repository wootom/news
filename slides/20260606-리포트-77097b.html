모델 개요 & 다운로드 사이즈 vs 구동 사이즈

📊 슬라이드
모델 개요
  • Google 공식 발표, Gemma 4 패밀리의 일원
  • 12B(12 Billion) 파라미터, 오픈소스·무료·로컬 실행 가능
  • Gemma 4 패밀리 라인업
2BGemma 4 2B (모바일 구동)
4BGemma 4 4B (모바일 구동)
12BGemma 4 12B (본 모델 — 16GB 디바이스)
26BGemma 4 26B (고성능, 16GB 초과)
31BGemma 4 31B (고성능, 16GB 초과)
  • 2B·4B: 모바일 구동 가능, 상대적으로 제한된 성능
  • 26B·31B: 성능 우수하나 16GB 디바이스에는 너무 큼
  • 12B: 26B 대비 동등 수준 성능 유지 + 16GB 디바이스 실행 가능 — Google 주장
다운로드 사이즈 vs 구동 사이즈
  • 파일 다운로드: 7.56 GB
  • 모델 메모리 로드 (4K context): 8 GB
  • 풀 컨텍스트 (131,072 tokens): 26 GB+ 필요
모델 용량 비교7.56 다운로드 크기
로드 시 필요 RAM8.0 기본 4K context
권장 실사용 (31K context)12.0 sweet spot
OS 점유 RAM2~3 macOS/Windows 기본
최대 컨텍스트 (131K)26.0 초과
  • OS (macOS/Windows)가 기본 2~3 GB 점유
  • 16GB 머신에서 실제 가용 RAM: 약 13~14 GB
  • 15 GB 이상 점유 시 시스템 크래시 위험

컨텍스트 길이별 RAM 요구량 & 성능: 12B vs 26B 벤치마크

📊 슬라이드
컨텍스트 길이별 RAM 요구량
4,000 tokens8 GB
8,000 tokens약 9 GB
16,000 tokens약 10 GB
31,000 tokens12 GB
65,536 tokens약 17 GB
131,072 tokens26 GB+
  • 31,000 tokens = 16GB 장비 한계선 (12 GB 소모 — 애매한 여유)
  • AI 에이전트 시스템(Claude Code, Codex, OpenClaw) 연동 시 베이스 프롬프트만 30,000~32,000 tokens
  • 기본 컨텍스트로는 Claude Code 등에서 첫 메시지부터 오류 발생 가능
성능: 12B vs 26B 벤치마크 비교 (지식창고 참조)
  • 평가 지표 (3대 축): 코딩 능력, 에이전틱 툴 콜링, 추론(Reasoning)
  • 12B 모델(연한 파랑)이 26B(진한 파랑) 대비 다수 지표에서 10% 이내 격차
Coding10 12B vs 26B 격차 (%), 낮을수록 근접
Agentic Tool Calling10 동일 (화자 강조 — 가장 중요한 지표)
Reasoning10 동일 수준
  • 파라미터 수는 절반 이하이나 성능 격차 10% 내외
  • 로컬 16GB 환경에서 이 수준 유지가 의미 있는 돌파구

인퍼런스 속도 & MTP — Multi-Token Pr

📊 슬라이드
인퍼런스 속도
  • 토큰 생성 속도: 11.69 tokens/sec (M4 Mac Mini, 16GB)
  • 첫 응답 처리: 92 tokens
  • 인퍼런스 2단계 구조
1. Pre-fill사용자 입력(프롬프트)을 모델이 읽고 소화하는 단계 — 메모리·연산 집중
2. Decoding소화 완료 후 응답 생성 단계 — 생성 속도 체감
  • M3 Ultra 관찰: Pre-fill은 느림, Decoding은 빠름
  • M4 Mac Mini: 실측 11.69 tokens/sec (대화용으로 무난)
MTP — Multi-Token Prediction
  • Gemma 4 12B의 핵심 신기술
  • Decoding 단계에만 적용 (Pre-fill 가속 없음)
  • 원리: 메인 모델(12B)과 함께 초소형 보조 모델 동봉
  • 보조 모델이 "다음 토큰"을 미리 예측, 메인 모델의 작업 부담 경감
Speedup1.5x ~ 1.8x
Acceptance Rate60~70%
  • 보조 모델 예측이 맞으면(60~70%) 메인 모델 생략 → 응답 시간 단축
  • 보조 모델이 틀리면 메인 모델이 정답 생성 (기존 방식 유지)

멀티모달 — 인코더 제거 아키텍처 & 실전 테스트 — 인보이스 OCR

📊 슬라이드
멀티모달 — 인코더 제거 아키텍처
  • 입력 지원: 텍스트 + 이미지 + 오디오
  • 기존 파이프라인 문제점
1. 인코더 분리 구조이미지 → 별도 Vision Encoder → 텍스트 변환 → LLM 입력 (지연·정확도 손실)
2. Gemma 4인코더 레이어 제거 → 입력이 직접 LLM으로 (속도·정확도 향상)
  • 별도의 Vision Encoder·Audio Encoder 파일 불필요
  • 종래 구조: 이미지 → Encoder(변환·지연) → LLM
  • Gemma 4: 이미지 → 바로 LLM
  • 화자 전언: "완전히 기술적이진 않지만, 이 구조가 더 빠르고 정확하다는 이해"
실전 테스트 — 인보이스 OCR
  • 테스트 이미지: Google 예시 인보이스
  • 요청: 인보이스 업로드 → 금액·Balance 추출
  • LM Studio 로컬 서버 연동 + VS Code HTML 앱 빌드
  • HTML 기반 Invoice Parser 데모 구현
Subtotal 실제 값13
Balance 실제 값1,298
Balance Gemma 추출1,296
판정부정확
  • Subtotal은 일치 (13)
  • Balance는 1,298 → 1,296으로 오차
  • 오픈소스 OCR 전용 모델(문서 텍스트 추출 특화)과 병렬 실행 → 검증 루틴 권장

LM Studio 셋업 포인트 & 실용 워크플로우 — 이메일 + 인보이

📊 슬라이드
LM Studio 셋업 포인트
  • LM Studio에서 모델 다운로드 (7.56 GB) → 서버 활성화
  • 로컬 서버 URL: http://localhost:1234 (LM Studio 기본)
  • 동적 로드 비활성화 → 수동 설정 권장
  • 멀티모달 토글 ON 필요 (이미지·오디오 처리용)
  • 컨텍스트 길이를 31,000 tokens 이하로 제한 → 16GB 환경 안정
기본 컨텍스트 (4K)8.0 RAM 소모 (GB)
실사용 권장 (31K)12.0 16GB 머신 한계
풀 컨텍스트 (131K)26.0 16GB 불가
OS 기본 점유2~3 macOS 최소 필요
실용 워크플로우 — 이메일 + 인보이스 자동화
  • 화자의 실제 목표: 16GB Mac Mini로 매주 1시간 절약
  • 인바운드 이메일 → 인보이스 첨부파일 → Gemma 4 OCR → DB 자동 기록
  • 스팸 필터링: 중요 클라이언트 메일 식별 및 우선 처리
  • 복수 모델 병렬 실행 전략
1. 인보이스 수신이메일 인박스 도착
2. Gemma 4 처리이미지 OCR + 금액 추출
3. 전용 OCR 모델병렬 실행 — 텍스트 검증
4. Python 스크립트규칙 기반 추가 검증
5. DB 기록검증 완료 후 자동 저장
  • 단일 모델 의존 대신 다중 모델+스크립트 검증 체인
  • 사람 개입(Human-in-the-loop) 없이 Self-validation 가능
