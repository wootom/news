버전 1.0의 문제점

📊 슬라이드
버전 1.0의 문제점
  • 오케스트레이터 종속성 문제

- 클로드 오퍼스 단일 오케스트레이터 고정 - 클로드 자체 약점이 시스템 전체 약점으로 노출 - GPT 5.5가 벤치마크에서 압도하는 상황에도 대응 불가 - 단일 벤더 종속성으로 인한 구조적 리스크

  • 높은 비용 부담

- 클로드 기본 구독 필요 - 코덱스 기본 구독 필요 - 제미나이 구독 필요 - 세 가지 플랫폼 구독을 동시에 유지해야 하는 비용 문제

  • 벤더 독립성 부족

- 특정 플랫폼에만 작동 - 플랫폼 정책 변화나 가격 인상 시 즉각 대응 불가

  • 설치 과정의 유연성 부족

- 환경 변화에 대응하기 어려운 구조 - 변경 시 재설치 부담

문제 축약단일 오케스트레이터 종속 → 벤더 리스크 집중
비용 문제3개 플랫폼 동시 구독 유지 부담
유연성플랫폼 종속 + 환경 변화 대응 어려움

버전 2.0의 핵심 해결책

📊 슬라이드
버전 2.0의 핵심 해결책
  • 플랫폼별 오케스트레이터 자동 변경 지원

- 클로드 코드(오퍼스)가 지휘자 역할 수행 - 코덱스(GPT 5.5)가 지휘자 역할 수행 - 앤티그래버티(제미나이 3.1)가 지휘자 역할 수행 - 세 가지 중 상황에 따라 선택 가능

  • 지휘자(오케스트레이터)만 변경하는 설계

- 워커 구성 변경 불필요 - 플러그인 구성 변경 불필요 - 폴더 구조 변경 불필요 - 작업 명령 변경 불필요 - 지휘자 교체만으로 전체 시스템 전환 가능

  • 이 설계의 핵심 가치

- 한 벤더의 정책 변화 발생 시 다른 벤더로 즉시 전환 - 한 벤더의 가격 인상 발생 시 다른 벤더로 즉시 전환 - 벤더 리스크를 시스템 전체 리스크로 확대하지 않음

  • 비용 최적화

- 앤티그래버티 CLI 무료 사용 가능 - 모델 조절 가능 설계로 비용 통제

  • 벤더 독립적 작동

- 어느 플랫폼에서나 자유롭게 작동 - 플랫폼 종속성 완전 제거

  • 플러그인 설치 방식

- 한 번 설치로 모든 폴더에서 편리하게 사용 - 자동 파일 준비 기능

3개지원 오케스트레이터 수 (클로드·코덱스·제미나이)
1개변경만 필요한 요소 (지휘자만)
0개변경 불필요한 요소 (워커·플러그인·폴더·명령)

기본 용어 및 개념

📊 슬라이드
기본 용어 및 개념
  • 핵심 역할 정의

- 한네스: 강력하지만 제어 불가능한 AI를 통제하는 제어 장치 - 오케스트레이터(지휘자): 작업 분배, 워커 지정, 최종 결과 통합 담당 - 워커: 실제 작업을 수행하는 AI 에이전트(클로드, 코덱스, 제미나이)

  • 작업 분배 패턴

- 팬아웃(Fan-out): 하나의 작업을 여러 워커에게 동시 분배 - 팬인(Fan-in): 여러 워커의 결과를 하나로 통합

1단계사용자 요청 → 오케스트레이터가 작업 분석
2단계팬아웃: 다수 워커에 동시 분배
3단계각 워커 독립적 작업 수행
4단계팬인: 오케스트레이터가 결과 통합

워커 호출 방식

📊 슬라이드
워커 호출 방식
  • 세 가지 호출 방식 존재

- 내장 호출: 같은 벤더 내 서브 에이전트 호출 - CLI 호출: 터미널 명령어로 외부 워커 호출 - MCP 호출: MCP(Model Context Protocol) 규격으로 외부 워커 호출

  • MCP 호출의 성격

- AI용 USB 포트에 비유 가능 - 표준화된 인터페이스로 외부 시스템 연결 - 플러그 앤 플레이 방식

  • 호출 방식 통합 관리

- 벤더마다 다른 호출 방식 존재 - 내장 함수 방식 지원 벤더 - MCP 방식 지원 벤더 - CLI 방식 지원 벤더 - API 방식 지원 벤더

  • backend.json 파일에 통합

- 디스패처(Dispatcher)가 자동 선택 - 각 환경에 최적 연결 방식 유지 - 시스템은 동일하게 작동

내장 호출 | 같은 벤더 내 서브 에이전트 | 빠름
CLI 호출 | 터미널 명령어 기반 | 벤더 독립
MCP 호출 | 표준 규격 연결 | AI용 USB 포트

워커 역할 분담

📊 슬라이드
워커 역할 분담
  • 역할별 전문성 할당

- 클로드 메인 워커: 코딩, 설계, 분석, 테스트, 이미지 생성 - 코덱스 메인 워커: 코딩, 설계, 분석, 테스트, 이미지 생성 - 크리틱 워커: 산출물 공격적 비판 및 검수

  • 크리틱 워커의 성과

- 평균 4~5개 문제 발견 - 원 작업자가 2~3개 수정 - 검수 품질이 개발 품질을 높이는 핵심

  • 제미나이 워커의 특화 역할

- 비전(Vision) 작업 처리 - 긴 문서 분석 수행 - 제3자 시각 검토 제공

4~5개크리틱 워커의 평균 문제 발견 수
2~3개원 작업자의 평균 수정 수
  • 검수 원칙

- 검수는 항상 지휘자(오케스트레이터)와 다른 벤더가 담당 - 자기 산출물 자체 검수 절대 금지 - 다른 개발 주체가 보는 다른 관점 필터링 활용 - 개발 주체가 다르면 놓치는 지점도 상이하다는 원칙

시스템 구성 및 작업 흐름

📊 슬라이드
시스템 구성 및 작업 흐름
  • 시스템 구성

- 제미나이가 오케스트레이터 역할 수행 - 멀티에이전트 2.0 플러그인 설치 필수 - 기본 설정만으로 시스템 구성 완료

  • 팬아웃-팬인 작업 방식 예시

- 주제: 향후 10년 AI 방향 - 팬아웃 단계: 클로드 워커 독립적 의견 제시, 코덱스 워커 독립적 의견 제시 - 팬인 단계: 지휘자(제미나이)가 자신의 관점 추가 후 통합 - 실행 순서: 클로드 먼저 완료, 코덱스 순차 완료

  • 작업 흐름 전체 구조

- 사용자 자연어 요청 입력 - 오케스트레이터가 task.md 자동 작성 - 워커 호출 시 사용자 승인 요청 - brief.md 작성 단계 - 워커 실행 단계 - 오케스트레이터가 result.md로 정리

1사용자 자연어 요청
2오케스트레이터 → task.md 자동 작성
3워커 호출 → 사용자 승인
4brief.md 작성
5워커 실행
6오케스트레이터 → result.md 정리

시연 내용

📊 슬라이드
시연 내용
  • MAP 기능 추가

- MAP: 멀티에이전트 트래킹 프로그램 - 클로드 코드에서 워커 호출 방식 표시 기능 - 각 워커가 어떤 방식으로 호출되었는지 시각적 확인 가능

  • 팬아웃-팬인 패턴 시연

- 팬아웃: 클로드, 코덱스, 제미나이 동시 호출하여 의견 수집 - 팬인: 지휘자(제미나이)가 자신의 관점 추가 후 전체 통합 - 코덱스 크리틱이 검수 단계 수행 - 검수 과정에서 버그 발견 및 수정 완료

  • PDF 분석 및 한글 문서 변환 시연

- 코덱스에서 PDF 수식 분석 수행 - 분석 결과를 한글 HWPX 문서로 변환 - HWPX MCP 이용하여 변환 작업 진행 - 수식 변환 일치 확인 완료 - 조립제법 부분만 미지원 상태 - 미지원 원인: 한글 수식 문법 부재 또는 제미나이 미인식 - 문서 작성에 다양하게 활용 가능

컨텍스트 엔지니어링 원칙

📊 슬라이드
컨텍스트 엔지니어링 원칙
  • 기본 원리(버전 1과 동일)

- 상태를 파일로 저장 - 승인 단계 거침 - 검증 단계 거침 - 컨텍스트 관리

  • 컨텍스트 비대화 방지

- context.md는 1,500자 제한 - brief.md는 1,200자 제한 - 짧고 핵심적인 정보만 유지

  • 파일 기반 정보 전달

- 긴 문서와 코드는 파일로 저장 - 컨텍스트에는 파일 경로만 전달 - 모델이 모든 내용을 직접 읽지 않도록 설계

  • 필요한 것만 필요할 때 호출

- 책상 위의 모든 서류를 펼쳐놓는 방식 지양 - 필요한 철(파일) 하나만 꺼내는 방식 지향 - 정보 접근의 경제성 원칙

  • 워커 결과 검증 사이클

- 워커가 결과 산출 - 다른 워커(크리틱)가 검수 - 검수 통과 시 최종 결과 확정 - 검수 실패 시 재작업

  • 브리프(brief.md) 작성 원칙

- 중요 목표는 앞쪽에 배치 - 중요 제약 조건은 앞쪽에 배치 - 금지사항은 끝쪽에 배치 - 이유: 모델이 중간 내용을 놓치는 경향이 있음 - 앞과 끝이 가장 잘 기억되는 위치
