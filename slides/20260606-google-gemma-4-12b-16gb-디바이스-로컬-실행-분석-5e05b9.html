모델 포지셔닝 & 성능 vs. 파라미터 효율

📊 슬라이드
모델 포지셔닝
  • Gemma 4 패밀리 라인업: E2B → E4B → 12B → 26B → 31B
  • E2B·E4B: 모바일 구동 가능 / 26B·31B: 16GB 디바이스 탑재 불가
  • 12B: 16GB RAM 디바이스(M4 Mac mini 등)에서 구동 가능한 상한선 모델
  • 오픈소스(무료 다운로드·로컬 실행) 라이선스

메모리 사용 실측 (M4 Mac mi & 컨텍스트 길이 운용 한계

📊 슬라이드
메모리 사용 실측 (M4 Mac mini 16GB)
  • 모델 다운로드 크기: 7.56 GB
  • 기본 로드(컨텍스트 4,000 토큰): ~8 GB
  • 31,000 토큰 컨텍스트 설정 시: ~12 GB 사용
  • 131,000 토큰(최대) 설정 시: 26 GB+ 필요 → 16GB 디바이스 실행 불가
  • 모델 로드 후 Activity Monitor 실측: 유휴 상태에서 14.9 GB 점유
  • OS·브라우저·앱 등 상시 2~3 GB 점유 → 실질 사용 가능 여유분 극소
컨텍스트 길이 운용 한계
  • 실용 스위트스팟: 31,000 토큰 (12 GB RAM 소요)
  • Claude Code·Codeware·Open Claude 등 AI 하네스의 기본 시스템 프롬프트 자체가 30,000~32,000 토큰 → 첫 메시지에서 컨텍스트 초과 에러 발생 가능
  • 결론: 31,000 토큰 = 로컬 AI 에이전트 연동 시 사실상 하한 임계치
Gemma 4 주요 아키텍처 업데이트 ①: 멀티모달 인코더 제거
  • 기존 방식: 이미지·오디오 입력 → 별도 인코더 파일 → LLM 순차 처리 → 레이턴시·번역 손실 발생
  • Gemma 4 방식: 인코더 기능을 LLM 내부에 통합 → 직접 입력 처리 → 속도·정확도 향상
  • 지원 입력 타입: 텍스트 · 이미지 · 오디오 (네이티브 멀티모달)
  • 활용 예: 에이전트에서 음성 메모·이미지를 중간 파이프라인 없이 직접 드롭인 가능

Gemma 4 주요 아키텍처 업데이트 & OCR·코딩 실사용 평가

📊 슬라이드
Gemma 4 주요 아키텍처 업데이트 ②: 멀티토큰 예측(MTP)
  • LLM 인퍼런스 2단계: 프리필(입력 소화) → 디코딩(응답 생성)
  • MTP 적용 구간: 디코딩 단계 한정 (프리필 속도에는 미영향)
  • 메커니즘: 소형 드래프트 모델이 다음 토큰을 사전 예측 → 메인 12B 모델의 검증 부담 경감
  • 드래프트 수락률: 일반적으로 60~70% 수준
  • 실측 속도 향상: 벤치마크 기준 1.5~1.8배 디코딩 속도 증가
  • 실측 토큰 생성 속도: 첫 응답 기준 ~11.69 토큰/초 (92 토큰 처리)
OCR·코딩 실사용 평가
  • 테스트: 샘플 인보이스 이미지 → Gemma 4 12B OCR 추출
  • 결과: Balance Due 수치 오추출 확인 (1298 → 1296 등 불일치)
  • 원인: 범용 모델 한계 → OCR 특화 오픈소스 모델과 병렬 실행·교차 검증 권장
  • 코딩 테스트: LM Studio 로컬 API(URL) → VS Code에서 HTML 인보이스 파서 생성 → 실행 성공 (OCR 정확도 이슈는 별개)
  • LM Studio 로컬 서버: 온/오프 토글 → 외부 앱에서 localhost URL로 모델 호출 가능
활용 시나리오 및 시사점
  • 적합 용도: 인보이스 처리 자동화·이메일 분류·멀티스텝 AI 워크플로우 (소규모 하드웨어 기반)
  • 제약: Claude Code 등 고컨텍스트 하네스 직접 연동 시 토큰 초과 에러 → 컨텍스트 최적화 필수
  • 권장 구성: 범용 LLM(Gemma 4 12B) + 도메인 특화 모델(OCR 전용 등) 병렬 파이프라인
  • 결론: 16GB 소형 디바이스에서 "진지한 AI 작업" 가능성을 열어준 첫 사례로 평가
