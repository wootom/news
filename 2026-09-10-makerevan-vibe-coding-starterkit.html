바이브 코딩 스타터킷은 구조와 규칙으로 AI 코드의 연속 개발을 돕는다.

구조·컨벤션·Docker 캐시로 AI 코드의 연속 개발 기반을 만드는 스타터킷.

01핵심 개요

  • AI가 만든 코드에 로그인·결제·주문 기능을 이어 붙이려면 긴 프롬프트보다 코드 자리와 연결 규칙이 필요하다고 설명한다.
  • 스타터킷은 Next.js·TypeScript·shadcn/ui를 프런트엔드 출발점으로 안내하며, 서비스별 변경에 집중하게 한다.
  • 회원·상품·주문을 업무 단위 도메인으로 나누고 API·서비스·데이터 저장 코드의 역할을 구분하는 방식을 제시한다.
  • Dockerfile 캐시와 개발·실행 결과물 분리, Python용 UV를 통해 배포 준비 시간을 줄이는 방법을 다룬다.
  • 규칙 문서와 컨벤션을 먼저 읽힌 뒤 기존 주문 도메인과 공통 오류 처리를 활용해 기능을 추가하는 흐름을 제안한다.

02핵심 주장 / 논점 구조

  • AI 코드의 일부를 고쳤을 때 다른 기능이 깨지는 문제는 프롬프트를 길게 쓰는 방식만으로 해결되지 않는다고 말한다.
  • 코드가 들어갈 자리와 코드 간 연결 규칙을 먼저 정해야 기존 코드를 버리지 않고 기능을 이어갈 수 있다고 설명한다.
  • 스타터킷은 모든 기능을 완성하는 제품이 아니라 구조와 규칙이 잡힌 출발점이며, 서비스 기능은 그 위에 만들어야 한다.
  • 이미 운영 중인 프로젝트는 통째로 바꾸기보다 필요한 규칙을 작은 범위부터 적용하고 기존 동작을 확인하라고 권한다.

03기술 스택을 팀 규모에 맞추는 출발점

  • 기술 스택은 화면·서버·데이터 저장소·서버 배포 방식을 정하는 가게의 설비 선택에 비유된다.
  • 유명한 기술을 모두 가져오는 것보다 만드는 팀이 다룰 수 있는 범위에 맞춰 선택해야 한다고 말한다.
  • 스타터킷 상세 페이지는 프런트엔드 구성으로 Next.js, TypeScript, shadcn/ui를 안내한다.
  • 출발점의 도구 구성을 맞추면 매번 도구부터 다시 고르지 않고 서비스에 필요한 부분을 바꿀 수 있다.

04도메인·API·서비스로 백엔드 책임 나누기

  • 영상에서 도메인은 인터넷 주소가 아니라 회원·상품·주문처럼 서비스가 맡는 업무를 뜻한다.
  • 회원 서류와 주문표를 한곳에 섞지 않듯 업무별 담당 영역을 나누면 사람과 AI가 관계를 파악하기 쉬워진다.
  • 주문 버튼이 눌리면 API는 주문을 받는 창구, 서비스는 재고 확인과 주문 처리 담당자, 데이터 저장 코드는 창고 담당으로 비유된다.
  • 도메인·서비스·API에 자리를 정하되, 폴더만 나누지 말고 서로의 내부 코드를 함부로 쓰지 않는 연결 규칙도 필요하다.
  • 처음부터 서버를 여러 개로 분리할 필요는 없으며, 한 서버 안에서도 업무와 책임을 나눌 수 있다고 설명한다.

05공통 부품 재사용과 변경 영향 확인

  • 날짜 표시 규칙을 세 화면에 복사하면 규칙 변경 시 세 번 수정해야 하고, 한곳을 놓치면 화면별 날짜가 달라질 수 있다.
  • 같은 책임의 코드를 공통 부품으로 만들면 새 화면에서 가져다 쓰며 관리할 수 있다.
  • 백엔드의 입력 확인과 공통 오류 처리처럼 반복되는 코드도 한곳에서 관리해 확인된 동작을 계속 활용할 수 있다.
  • 회원 기능과 배송비 할인처럼 나중에 규칙이 달라질 수 있는 코드는 비슷해 보여도 무조건 하나로 합치면 안 된다고 말한다.
  • 공통 부품을 바꾼 뒤에는 사용하는 곳도 함께 확인해야 하며, 재사용 자체가 자동으로 버그를 없애지는 않는다.

06AI 컨텍스트와 규칙 문서의 활용

  • 컨텍스트는 AI가 현재 펼쳐 놓고 읽는 작업 책상에 비유되며, 주문 기능 수정에 모든 파일을 올리면 복잡해진다.
  • 업무 분리와 명확한 연결 규칙이 있으면 AI가 필요한 영역부터 보고, 공통 부품 내부를 매번 새로 만들 필요도 줄어든다.
  • AI가 실제로 읽는 파일에 따라 효과는 달라지므로 컨텍스트를 전혀 쓰지 않는다는 뜻은 아니라고 선을 긋는다.
  • 새 대화에서도 규칙 문서를 읽고 같은 기준에서 작업하게 하면 기존 코드를 계속 이어갈 수 있다고 설명한다.
  • 예시 요청으로 기존 규칙과 주문 도메인을 확인한 뒤 공통 오류 처리를 재사용해 취소 기능을 추가하는 방식을 든다.

07Dockerfile 캐시와 UV 패키지 설치

  • Docker 이미지는 프로그램 실행 준비물이 든 상자이고, Dockerfile은 그 상자를 만드는 순서를 적은 설명서로 설명된다.
  • 실행에 필요한 것만 이미지에 남기면 이미지 크기와 전송 부담을 줄일 수 있으며, 개발용 도구와 실행용 결과물을 나누는 방법도 소개한다.
  • 변경이 적은 준비물 목록을 소스 코드보다 먼저 처리하면 이전 설치 결과를 재사용하는 빌드 캐시를 활용할 수 있다.
  • 준비물 목록이나 앞 단계가 바뀌면 다시 만드는 구간이 생기므로 캐시가 항상 유지되지는 않는다고 설명한다.
  • Python 백엔드에서는 UV를 사용할 수 있으며, 공식 문서는 pip보다 패키지 작업이 10배에서 100배 빠르다고 소개한다고 말한다.
  • UV 잠금 파일과 스타터킷 적용 범위: UV의 잠금 파일은 사용할 패키지 버전 조합을 기록해 로컬 컴퓨터와 배포 환경의 준비물을 맞추는 데 활용된다.
  • UV 잠금 파일과 스타터킷 적용 범위: UV의 속도 수치는 패키지 작업 벤치마크이며, 모든 배포가 100배 빨라진다는 뜻은 아니라고 설명한다.
  • UV 잠금 파일과 스타터킷 적용 범위: 실제 차이는 패키지 구성·네트워크·캐시 상태에 따라 달라지고, 테스트나 이미지 전송이 오래 걸리면 그 부분도 따로 살펴야 한다.
  • UV 잠금 파일과 스타터킷 적용 범위: 스타터킷에는 구조와 컨벤션이 함께 들어 있으며, 프로젝트에 맞게 바꾸더라도 문서와 코드의 기준을 함께 맞춰야 한다.
  • UV 잠금 파일과 스타터킷 적용 범위: 새 프로젝트에서는 규칙을 읽은 뒤 작은 기능 하나를 끝까지 붙이며 파일 위치와 공통 코드 사용 방식을 확인하라고 제안한다.

08용어 사전

용어뜻
도메인회원·상품·주문처럼 서비스가 맡는 업무 단위이며, 인터넷 주소를 뜻하는 용어로 사용되지 않는다.
API손님의 주문을 받는 창구에 비유되며, 주문 요청을 받아 서비스 영역으로 전달하는 역할이다.
서비스주문 처리와 재고 확인처럼 업무 로직을 담당하는 코드 영역으로 설명된다.
빌드 캐시변경되지 않은 준비물의 설치 결과를 다시 사용해 코드 수정 때 모든 패키지를 재설치하지 않게 하는 방식이다.
UVPython 백엔드에서 패키지를 찾고 설치하는 도구로, 잠금 파일을 통해 패키지 버전 조합도 기록한다.
컨벤션파일 이름, 폴더 위치, 오류 반환, 공통 코드 사용 위치 등을 프로젝트에서 함께 지키는 약속이다.
